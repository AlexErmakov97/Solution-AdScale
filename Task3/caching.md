# Стратегия кеширования

Диаграмма:

- `diagrams/cache-architecture.puml`

## 1. Зачем кеш и главный принцип

Hot path должен уложиться в 25–35 мс внутри Сервиса ставок при 50 000 RPS. Данные, нужные аукциону, меняются редко, а
читаются на каждом запросе, — значит, их нужно держать как можно ближе к коду.

**Принцип:** кеш на hot path — не «ускоритель базы», а **единственный источник данных для решения о ставке**. Базу
данных аукцион не видит совсем. Поэтому кеш обновляется событиями заранее (push), а не заполняется при промахе (pull):
промах на hot path означал бы поход в БД, а это ровно то, что мы устраняем.

## 2. Уровни кеша

| Уровень              | Где                                                          | Задержка                   | Что хранит                                                                                                                                   |
|:---------------------|:-------------------------------------------------------------|:---------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------|
| L1 — память процесса | каждый под Сервиса ставок, Bid Gateway, Delivery             | наносекунды – микросекунды | кампании, таргетинг, креативы, ставки кампаний, последний статус бюджета, шаблоны разметки, кешированные ставки для резервного ответа        |
| L2 — Redis Cluster   | в каждом регионе, в тех же зонах доступности, что и hot path | < 1 мс                     | данные, которые меняются часто или не помещаются в память пода: профили пользователей, счётчики частоты, оперативный статус бюджета и pacing |
| CDN                  | у пользователя                                               | —                          | изображения, видео и скрипты баннеров                                                                                                        |

**Почему кампании — в памяти, а не в Redis.** Кампаний тысячи, весь индекс — сотни мегабайт, он помещается в память
каждого пода. Подбор кандидатов — это пересечение множеств по нескольким индексам: в памяти — микросекунды, через
Redis — десятки сетевых вызовов.

**Почему профили — в Redis, а не в памяти.** Пользователей — десятки миллионов; профиль нужен на каждый запрос, но для
разных пользователей. Копию на каждом поде держать невозможно.

## 3. Что кешировать

| Данные                                           | Уровень                       | Источник истины                          | Объём (оценка) | Чтений / с                      |
|:-------------------------------------------------|:------------------------------|:-----------------------------------------|:---------------|:--------------------------------|
| Кампании: статус, стратегия, бюджеты, расписание | L1                            | Сервис кампаний                          | тысячи записей | 50 000+                         |
| Ставки кампаний (максимальная, по умолчанию)     | L1, в составе кампании        | Сервис кампаний                          | —              | 50 000+                         |
| Таргетинг и инвертированные индексы              | L1                            | Сервис кампаний                          | сотни МБ       | 50 000+                         |
| Креативы (метаданные) и шаблоны разметки         | L1 (Сервис ставок, Delivery)  | Сервис кампаний                          | десятки МБ     | ~10 000                         |
| Статус бюджета и pacing                          | L2 + последний известный в L1 | Budget & Pacing                          | тысячи ключей  | 50 000+                         |
| Профили и сегменты пользователей                 | L2                            | обработка событий (история — ClickHouse) | десятки ГБ     | 50 000+                         |
| Счётчики частоты показов                         | L2                            | Сервис статистики                        | гигабайты      | 50 000+                         |
| Кешированные ставки для резервного ответа        | L1 Bid Gateway                | Сервис ставок                            | тысячи записей | только при открытом размыкателе |
| Ключи дедупликации уведомлений                   | L2 (отдельный Redis)          | Event Collector                          | гигабайты      | ~10 000                         |
| Результаты отчётов кабинета                      | L2 (отдельный Redis)          | Сервис аналитики                         | гигабайты      | сотни                           |
| Остаток бюджета для показа в кабинете            | — (не кешируется)             | Сервис финансов                          | —              | —                               |

Точный баланс рекламодателя не кешируется: он читается с primary-узла Сервиса финансов, чтобы кабинет не показывал
устаревшие деньги.

## 4. Где разместить Redis

| Экземпляр       | Назначение                               | Размещение                                                            | Конфигурация                                                                                                    |
|:----------------|:-----------------------------------------|:----------------------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------|
| **redis-rtb**   | профили, частоты, статус бюджета, pacing | в каждом регионе hot path, в тех же зонах доступности, отдельные узлы | Redis Cluster: 3 шарда × (primary + реплика в другой зоне), без постоянного хранения кроме RDB-снимков профилей |
| **redis-dedup** | дедупликация `nurl` / `burl`             | в каждом регионе                                                      | primary + реплика, AOF (каждую секунду)                                                                         |
| **redis-app**   | кеш отчётов и сессий кабинета            | основной регион back-office                                           | primary + реплика                                                                                               |

**Почему три экземпляра, а не один:**

- изоляция: тяжёлый отчёт или всплеск уведомлений не должен вытеснять профили и замедлять hot path;
- разные политики: в `redis-rtb` вытеснение по LRU допустимо (профиль — не критичные данные), в `redis-dedup` вытеснение
  недопустимо (`noeviction`), иначе возможен повтор списания;
- разное размещение: hot path — в каждом регионе, кабинет — в основном.

## 5. TTL

| Ключ / данные                                  | TTL                                                                                                             | Почему                                                                                                         |
|:-----------------------------------------------|:----------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------|
| Кампании, таргетинг, креативы (L1)             | без TTL, обновление событиями; **контроль свежести**: отставание индекса > 30 с → под выводится из балансировки | TTL здесь опасен: истечение означало бы промах на hot path                                                     |
| `user:{uid}` — профиль                         | 30 дней со скользящим продлением при обновлении                                                                 | неактивные пользователи уходят сами, память не растёт бесконечно                                               |
| `freq:{uid}:{campaign_id}` — частота           | 24 ч                                                                                                            | частотный лимит считается за сутки                                                                             |
| `budget:status:{campaign_id}`                  | 24 ч (страховка); фактически перезаписывается при каждом изменении                                              | при остановке Budget & Pacing статус не «застывает» навсегда                                                   |
| `pacing:{campaign_id}`                         | 10 мин                                                                                                          | если Budget & Pacing не обновил коэффициент 10 минут — используется ставка по умолчанию и консервативный режим |
| Кешированная ставка в Bid Gateway              | 60 с                                                                                                            | резервный ответ не должен опираться на устаревшие цены                                                         |
| `bill:{bid_id}`, `win:{bid_id}` — дедупликация | 24 ч                                                                                                            | партнёры повторяют уведомления в пределах суток                                                                |
| Отчёт кабинета                                 | 60 с для «сегодня», 1 ч для закрытых периодов                                                                   | данные за прошлые дни не меняются                                                                              |

**Разброс TTL (jitter ±10%)** для массово создаваемых ключей, чтобы они не истекали одновременно.

## 6. Стратегия инвалидации

| Данные                           | Стратегия                                  | Как работает                                                                                                                                                                                                         |
|:---------------------------------|:-------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Кампании, ставки, таргетинг (L1) | **событийное обновление (push)**           | Сервис кампаний в одной транзакции меняет данные и пишет событие в outbox → `campaign-changes` → каждый под Сервиса ставок применяет изменение. Событие несёт `version`: устаревшие и повторные события игнорируются |
| Статус бюджета и pacing          | **write-through** от владельца             | Budget & Pacing записывает новое значение в Redis и публикует `budget-status`; Сервис ставок обновляет копию в памяти                                                                                                |
| Профили, частоты                 | **запись при обработке событий** + TTL     | Stats Processor обновляет профиль и инкрементирует частоту; инвалидация не нужна                                                                                                                                     |
| Отчёты кабинета                  | **cache-aside** + версия данных в ключе    | ключ = параметры отчёта + номер последней загруженной партии агрегатов; новая партия — новый ключ, старые истекают по TTL                                                                                            |
| Кешированные ставки              | TTL + сброс по `budget-status = exhausted` | кампания без бюджета исключается из резервных ответов сразу                                                                                                                                                          |

**Почему не «удалить ключ при изменении»:** удаление на hot path вызвало бы промах. Схема «сначала в БД, потом событие»
с версиями даёт согласованность в конечном счёте за 1–5 с без промахов.

**Защита от расхождений:**

- раз в 10 минут Сервис ставок сверяет контрольные суммы версий своего индекса с Сервисом кампаний; при расхождении —
  полная перезагрузка снимка;
- метрики: отставание обработки `campaign-changes`, возраст последнего обновления `pacing`, доля промахов профилей.

## 7. Прогрев кеша (cache warming)

| Ситуация                                               | Как прогреваем                                                                                                                                                              | Пока прогрев не закончен                                                                                             |
|:-------------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------|
| **Старт пода Сервиса ставок** (релиз, масштабирование) | снимок активных кампаний из Сервиса кампаний (gRPC stream, с асинхронной реплики) → догон `campaign-changes` и `budget-status` с позиции снимка                             | readiness = false: под не получает трафик                                                                            |
| **Масштабирование на пик**                             | HPA с запасом (цель CPU 60%) и плановое увеличение подов перед известными пиками (вечерние часы)                                                                            | новые поды прогреваются 30–60 с — поэтому масштабирование заранее, а не по факту перегрузки                          |
| **Сбой узла Redis**                                    | реплика становится primary автоматически, данные уже в ней                                                                                                                  | —                                                                                                                    |
| **Полная потеря redis-rtb**                            | профили: загрузка RDB-снимка или пересборка из ClickHouse для пользователей, активных за 7 дней, с ограничением скорости; бюджеты: Budget & Pacing пересчитывает из `spend` | Сервис ставок работает на резервных стратегиях: контекстный таргетинг, статус бюджета из памяти, ставка по умолчанию |
| **Новый регион**                                       | развернуть redis-rtb, загрузить профили из снимка, поднять поды Сервиса ставок, дождаться готовности                                                                        | трафик на регион не направляется (Global LB) до прохождения проверок                                                 |
| **Отчёты кабинета**                                    | ленивое заполнение (cache-aside); популярные отчёты «за вчера» считаются заранее ночным заданием                                                                            | при одновременных одинаковых запросах выполняется один расчёт, остальные ждут его результат (request coalescing)     |

## 8. Метрики кеша

| Метрика                                           | Цель / алерт                                                |
|:--------------------------------------------------|:------------------------------------------------------------|
| Отставание индекса кампаний от `campaign-changes` | ≤ 5 с; алерт > 30 с                                         |
| Доля промахов профилей (redis-rtb)                | наблюдается; алерт при резком росте (признак потери данных) |
| Задержка Redis P99                                | ≤ 1 мс; алерт > 3 мс                                        |
| Использование памяти Redis                        | алерт > 75%                                                 |
| Доля ответов на резервных стратегиях              | алерт > 5%                                                  |
| Попадания в кеш отчётов                           | ≥ 70%                                                       |
