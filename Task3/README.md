# AdScale: данные, масштабирование и отказоустойчивость

## Задача

Спроектировать стратегию работы с данными для микросервисной архитектуры AdScale: выбрать хранилище для
каждого сервиса, определить репликацию и шардирование, спроектировать кеширование и потоковую обработку событий, задать
RPO и RTO и стратегию резервного копирования. Нагрузка: 18 000 RPS через 3 месяца, 50 000 RPS через год, доступность
99.9%.

## Ключевые решения

1. **Database per Service, хранилище — под профиль нагрузки:**

| Сервис     | Хранилище                             |
|:-----------|:--------------------------------------|
| ставок     | своей БД нет: индекс в памяти + Redis |
| кампаний   | PostgreSQL                            |
| статистики | ClickHouse                            |
| аналитики  | собственные витрины в ClickHouse      |
| финансов   | PostgreSQL                            |

Обмен данными между сервисами — только через API и Kafka.

2. **Масштабирование:**
    - primary + синхронный standby + асинхронная реплика — для PostgreSQL кампаний и финансов (нагрузка на запись
      невелика, важна надёжность);
    - шардирование — только там, где объём растёт с трафиком: ClickHouse (сырые события по `bid_id`, агрегаты по
      `advertiser_id`), Redis Cluster, партиции Kafka;
    - read replica PostgreSQL для аналитики — на этапе 1; в целевом решении аналитика уходит на реплики ClickHouse;
    - CQRS: кампании → индекс ставок, события → витрины, ledger → баланс, финансы → оперативный бюджет.
3. **Кеш на hot path — единственный источник данных для решения о ставке:**
    - обновляется событиями заранее (push), а не при промахе;
    - два уровня: память процесса и Redis;
    - три отдельных экземпляра Redis по назначению;
    - прогрев с контролем готовности пода.
4. **Kafka:**
    - 7 топиков трёх классов: сырые, денежные, состояние;
    - Avro + Schema Registry с режимом BACKWARD_TRANSITIVE;
    - группы потребителей с идемпотентной обработкой;
    - хранение от 3 до 30 дней по ценности данных;
    - около 8–11 ТБ дисков на регион через год.
5. **Отказоустойчивость:**
    - RPO = 0 для финансов и кампаний;
    - сырые события восстанавливаются из Kafka;
    - PITR для PostgreSQL;
    - ежемесячная проверка восстановления;
    - соответствие 12 факторам.
