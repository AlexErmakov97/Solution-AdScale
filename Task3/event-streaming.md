# Архитектура потоковой обработки событий (Kafka)

Диаграмма:

- `diagrams/event-flow.puml`

## 1. Общая схема

```
Сервис ставок ──bids──────────┐
Event Collector ──wins────────┤
                ──impressions─┼──▶ Stats Processor (Kafka Streams) ──▶ ClickHouse (статистика)
                ──clicks──────┘          │  дедупликация, обогащение,
                                         │  агрегация по кампаниям за 10 с
                                         └──spend──▶ Budget & Pacing ──budget-status──▶ Сервис ставок, Сервис кампаний
                                                 └──▶ Сервис финансов (ledger)
wins, impressions, clicks, spend ──▶ Reporting Loader ──▶ ClickHouse (витрины аналитики)
Сервис кампаний ──outbox──campaign-changes──▶ Сервис ставок (каждый под)
```

Три класса топиков:

- **сырые события** — что произошло (ставка, выигрыш, показ, клик): большой объём, хранение по времени;
- **производные события** — результат обработки (расход по кампаниям): средний объём, денежные данные, хранение дольше;
- **топики состояния** — последнее состояние сущности (изменения кампаний, статус бюджета): compacted, по ключу хранится
  последнее значение.

## 2. Топики

Общие настройки кластера: фактор репликации 3 (по одной реплике в каждой зоне доступности), `min.insync.replicas=2`,
сжатие `zstd` на стороне продюсера, ключ партиционирования — `campaign_id` (порядок событий одной кампании сохраняется).

| Топик                         | Класс                 | Продюсер                 | Партиций        | `acks` | Очистка | Хранение                           |
|:------------------------------|:----------------------|:-------------------------|:----------------|:-------|:--------|:-----------------------------------|
| `bids`                        | сырые                 | Сервис ставок            | 48              | 1      | delete  | 3 дня                              |
| `wins`                        | сырые, денежные       | Event Collector          | 24              | all    | delete  | 7 дней                             |
| `impressions`                 | сырые, денежные       | Event Collector          | 48              | all    | delete  | 7 дней                             |
| `clicks`                      | сырые, денежные       | Event Collector          | 12              | all    | delete  | 7 дней                             |
| `spend`                       | производные, денежные | Stats Processor          | 12              | all    | delete  | 30 дней                            |
| `budget-status`               | состояние             | Budget & Pacing          | 6               | all    | compact | последнее значение по кампании     |
| `campaign-changes`            | состояние             | Сервис кампаний (outbox) | 6               | all    | compact | последнее значение по кампании     |
| `<topic>.dlq`                 | ошибки обработки      | потребители              | 3               | all    | delete  | 14 дней                            |
| `stats-processor-*-changelog` | служебные             | Kafka Streams            | как у источника | all    | compact | состояние дедупликации и агрегатов |

**Почему так:**

- `bids` с `acks=1`: аналитический поток, самый большой; редкая потеря при сбое брокера допустима ради минимальной
  задержки продюсера. Денежные топики — только `acks=all` и идемпотентный продюсер.
- **48 партиций** для самых больших топиков: при 50 000 событий/с это ~1 000 событий/с на партицию — большой запас;
  число партиций ограничивает число параллельных потребителей, поэтому закладываем с запасом на рост, а уменьшить потом
  нельзя.
- **`spend` хранится 30 дней**: это журнал, из которого Сервис финансов может переобработать списания после сбоя (RPO
  финансов, `database-strategy.md`).

## 3. Схема событий: Avro

### 3.1. Почему Avro, а не JSON

| Критерий                   | Avro + Schema Registry                                                                                   | JSON                                                                        |
|:---------------------------|:---------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------|
| Размер сообщения           | бинарный, без имён полей: в 2–4 раза меньше                                                              | имена полей в каждом сообщении                                              |
| Объём при 50 000 событий/с | ~15 МБ/с только `bids`                                                                                   | ~40–50 МБ/с — в 3 раза дороже хранение, сеть и диски брокеров               |
| Контроль схемы             | реестр проверяет каждую новую версию на совместимость; продюсер не может отправить несовместимое событие | схема не обязательна; ошибка продюсера ломает потребителей уже в продакшене |
| Эволюция                   | правила добавления полей со значениями по умолчанию, старые и новые версии читаются вместе               | договорённости вручную                                                      |
| Экосистема                 | Kafka Streams, Kafka Connect, Flink, ClickHouse читают Avro напрямую                                     | универсально                                                                |
| Читаемость при отладке     | нужен инструмент (реестр + консольный потребитель)                                                       | читается глазами                                                            |

Решающие аргументы — объём (поток самый большой в системе) и защита от несовместимых изменений между командами.
Неудобство отладки закрывается инструментами реестра. JSON остаётся для внешних интерфейсов (OpenRTB, REST кабинета).

**Реестр схем:** Schema Registry с открытой лицензией (Karapace или Apicurio) или управляемый сервис облака;
именование — по топику (`<topic>-value`).

### 3.2. Совместимость и правила изменений

- Режим совместимости — **BACKWARD_TRANSITIVE**: новая схема читает все старые версии. Порядок выкатки: сначала
  потребители, потом продюсеры.
- Разрешено: добавить поле **со значением по умолчанию**; удалить поле, у которого было значение по умолчанию.
- Запрещено: переименовать поле, сменить тип, добавить поле без значения по умолчанию. Такое изменение — новая версия
  события в новом топике с периодом параллельной публикации.
- Суммы — только целые числа (`long`, микро-единицы валюты), время — `timestamp-millis`, идентификаторы — строки (UUID).

### 3.3. Общие поля (конверт) всех событий

| Поле          | Тип              | Назначение                                                                |
|:--------------|:-----------------|:--------------------------------------------------------------------------|
| `event_id`    | string (UUID)    | уникальный id события — ключ дедупликации                                 |
| `event_type`  | string           | тип события                                                               |
| `occurred_at` | timestamp-millis | когда событие произошло (время события, по нему считаются окна агрегации) |
| `produced_at` | timestamp-millis | когда опубликовано (для измерения задержки конвейера)                     |
| `source`      | string           | сервис-продюсер и его версия                                              |
| `region`      | string           | регион                                                                    |
| `trace_id`    | string, optional | связь с трассировкой OpenTelemetry                                        |

### 3.4. События

| Событие (топик)                           | Ключевые поля помимо конверта                                                                                                                                                                                                                                                                                      |
|:------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| BidEvent (`bids`)                         | `bid_id`, `request_id`, `partner_id`, `imp_id`, `campaign_id`, `creative_id`, `price_micros`, `currency`, `outcome` (bid / no_bid), `no_bid_reason`, `fallback_flags`, `latency_ms`                                                                                                                                |
| WinEvent (`wins`)                         | `bid_id`, `partner_id`, `campaign_id`, `creative_id`, `clearing_price_micros` (цена, по которой выиграли)                                                                                                                                                                                                          |
| ImpressionEvent (`impressions`)           | `bid_id`, `campaign_id`, `creative_id`, `advertiser_id`, `user_id`, `site_domain` / `app_bundle`, `cost_micros`                                                                                                                                                                                                    |
| ClickEvent (`clicks`)                     | `bid_id`, `click_id`, `campaign_id`, `creative_id`, `advertiser_id`, `user_id`, `cost_micros` (для CPC-кампаний)                                                                                                                                                                                                   |
| SpendEvent (`spend`)                      | `spend_id` (= `campaign_id` + начало окна — ключ идемпотентности списания), `campaign_id`, `advertiser_id`, `window_start`, `window_end`, `impressions`, `clicks`, `amount_micros`, `currency`                                                                                                                     |
| BudgetStatusEvent (`budget-status`)       | `campaign_id`, `status` (ok / throttled / exhausted), `pacing_rate`, `spent_today_micros`, `daily_budget_micros`, `version`                                                                                                                                                                                        |
| CampaignChangedEvent (`campaign-changes`) | `campaign_id`, `version`, `change_type` (created / updated / paused / deleted), полное состояние кампании: стратегия, ставки, бюджет, расписание, таргетинг, креативы. Полное состояние, а не разница: compacted-топик хранит только последнее сообщение по ключу, и новый потребитель восстанавливает всё из него |

## 4. Группы потребителей

| Группа                   | Сервис                            | Топики                                                              | Экземпляров (макс.) | Гарантия                                                                                                         | Фиксация смещения                                    |
|:-------------------------|:----------------------------------|:--------------------------------------------------------------------|:--------------------|:-----------------------------------------------------------------------------------------------------------------|:-----------------------------------------------------|
| `stats-processor`        | Сервис статистики (Kafka Streams) | `bids`, `wins`, `impressions`, `clicks` → пишет `spend`, ClickHouse | до 48               | exactly-once внутри Kafka (`exactly_once_v2`); в ClickHouse — идемпотентная вставка (дедупликация по `event_id`) | транзакционно вместе с выходными сообщениями         |
| `reporting-loader`       | Сервис аналитики                  | `wins`, `impressions`, `clicks`, `spend`                            | до 48               | at-least-once + дедупликация в ClickHouse (ReplacingMergeTree по `event_id`)                                     | после успешной вставки пакета                        |
| `budget-pacing`          | Budget & Pacing                   | `spend`                                                             | до 12               | at-least-once, идемпотентно по `spend_id`                                                                        | после обновления счётчиков                           |
| `billing`                | Сервис финансов                   | `spend`                                                             | до 12               | at-least-once, идемпотентно: уникальный `source_id` в ledger                                                     | после фиксации транзакции в БД                       |
| `campaign-budget-status` | Сервис кампаний                   | `budget-status`                                                     | до 6                | at-least-once, по `version`                                                                                      | после обновления статуса                             |
| без группы (`assign`)    | Сервис ставок, каждый под         | `campaign-changes`, `budget-status` — **все партиции**              | —                   | каждый под читает полный поток, применяет по `version`                                                           | не фиксируется: позиция берётся из снимка при старте |
| `dlq-handler`            | инструмент поддержки              | `*.dlq`                                                             | 1                   | ручной разбор и повторная отправка                                                                               | —                                                    |

**Почему Сервис ставок читает без группы:** в группе каждая партиция достаётся одному потребителю, а каждому поду нужны
**все** изменения кампаний — у каждого своя полная копия индекса. Поэтому под назначает себе все партиции сам и не
фиксирует смещения: при перезапуске он всё равно загружает свежий снимок.

**Масштабирование потребителей:** экземпляров в группе — не больше числа партиций; рост выше — через увеличение партиций
(планируется заранее, раздел 2).

**Ошибки обработки:** повторы с экспоненциальной задержкой (200 мс × 2ⁿ, до 30 с, jitter); после 5 неудач — сообщение в
`<topic>.dlq` с причиной и алерт. Обработка остальных сообщений не останавливается.

## 5. Политика хранения

| Топик                               | Хранение                                                           | Обоснование                                                                                                             |
|:------------------------------------|:-------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------|
| `bids`                              | 3 дня                                                              | самый большой поток; после загрузки в ClickHouse нужен только для повторной обработки после сбоя — за выходные          |
| `wins`, `impressions`, `clicks`     | 7 дней                                                             | денежные события: неделя на обнаружение ошибки в обработке и переобработку                                              |
| `spend`                             | 30 дней                                                            | журнал для восстановления и сверки финансов за месяц                                                                    |
| `campaign-changes`, `budget-status` | compact, без ограничения по времени; `min.compaction.lag.ms` = 1 ч | хранится последнее состояние каждой кампании; удалённая кампания — сообщение-«надгробие» (tombstone) с пустым значением |
| `*.dlq`                             | 14 дней                                                            | время на разбор                                                                                                         |
| changelog Kafka Streams             | compact                                                            | восстановление состояния процессора                                                                                     |

Долгосрочное хранение событий — не в Kafka, а в ClickHouse (`scaling.md`, раздел 4.1): Kafka — журнал для доставки и
переобработки, а не архив.

### 5.1. Оценка объёма дисков (через год, 50 000 RPS)

| Топик                  | Событий/с | Размер Avro | Поток    | В сутки  | × репликация 3 | × хранение      |
|:-----------------------|:----------|:------------|:---------|:---------|:---------------|:----------------|
| `bids`                 | 50 000    | ~300 Б      | 15 МБ/с  | ~1,3 ТБ  | ~3,9 ТБ        | 3 дня ≈ 11,7 ТБ |
| `wins` + `impressions` | ~20 000   | ~250 Б      | 5 МБ/с   | ~0,43 ТБ | ~1,3 ТБ        | 7 дней ≈ 9 ТБ   |
| остальные              | —         | —           | < 1 МБ/с | —        | —              | < 1 ТБ          |
| **Итого** до сжатия    |           |             |          |          |                | **≈ 22 ТБ**     |

С сжатием `zstd` (ориентир — в 2–3 раза) — около **8–11 ТБ** на кластер региона. Оценка уточняется по фактическому
размеру сообщений.

## 6. Мультирегиональность

- В каждом регионе — свой кластер Kafka: сервисы hot path пишут и читают только локально (задержка и независимость при
  сбое связи между регионами).
- **MirrorMaker 2** реплицирует:
    - из регионов в основной: `wins`, `impressions`, `clicks`, `spend` — для статистики, аналитики и финансов, которые
      работают в основном регионе;
    - из основного в регионы: `campaign-changes`, `budget-status` — для Сервиса ставок.
- Реплицированные топики получают префикс региона (`eu1.impressions`), потребители в основном регионе читают все
  региональные копии.
- При потере связи события накапливаются в региональном кластере (7 дней) и доставляются после восстановления.

## 7. Мониторинг

| Метрика                                               | Алерт            |
|:------------------------------------------------------|:-----------------|
| Отставание группы `billing`, `budget-pacing`          | > 1 мин          |
| Отставание `stats-processor`                          | > 2 мин          |
| Отставание `reporting-loader`                         | > 15 мин         |
| Отставание подов Сервиса ставок по `campaign-changes` | > 30 с           |
| Недореплицированные партиции                          | > 0 дольше 5 мин |
| Задержка публикации (P99)                             | > 20 мс          |
| Новые сообщения в DLQ                                 | любые            |
| Отказы реестра схем при публикации                    | любые            |
