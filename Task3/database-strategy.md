# Стратегия данных: Database per Service и отказоустойчивость

Выбор хранилища для каждого сервиса и отказоустойчивость данных (RPO, RTO,
резервное копирование, 12 факторов). Репликация и шардирование подробно — в `scaling.md`, кеш — в `caching.md`, Kafka —
в `event-streaming.md`.

Диаграмма:

- `diagrams/data-ownership.puml`

## 1. Принципы

1. **У каждого сервиса свои данные.** Другой сервис не читает и не пишет чужие таблицы напрямую — только через API или
   события Kafka. Так сервисы можно менять, масштабировать и восстанавливать независимо.
2. **Хранилище выбирается под профиль нагрузки**, а не одно на всех: транзакции, высокочастотная запись, аналитические
   запросы и чтение за миллисекунды требуют разных СУБД. Именно смешение этих профилей в одной PostgreSQL — главная
   проблема AS-IS.
3. **Источник истины у каждого вида данных один.** Остальные копии (кеш, индекс в памяти, витрины отчётов) —
   производные: их можно пересобрать из источника или из событий.
4. **Минимум разных технологий.** Команда без SRE: используются четыре хранилища (PostgreSQL, ClickHouse, Redis, Kafka),
   по возможности как управляемые сервисы.

## 2. Выбор базы данных для каждого сервиса

| Сервис                                         | Тип базы данных                                                                                                          | Обоснование                                                                                                                                                                                                                                                                                                                                                                                     |
|:-----------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Сервис ставок** (Bidding Service)            | **Своей постоянной БД нет.** Индекс кампаний в памяти процесса + Redis Cluster (key-value в памяти)                      | Hot path с бюджетом 25–35 мс на сервис: ни одного обращения к дисковой БД. Данные только читаются: кампании и ставки приходят снимком и событиями от Сервиса кампаний и лежат в памяти; профили пользователей, статус бюджета и частоты показов — в Redis (чтение < 1 мс). Всё это производные данные, которые восстанавливаются из источников (см. `caching.md`)                               |
| **Сервис кампаний** (Campaign Service)         | **PostgreSQL** (реляционная, OLTP)                                                                                       | Кампании, таргетинг, креативы, ставки — связанные сущности с ограничениями целостности (у креатива есть кампания, у кампании — рекламодатель). Нужны транзакции: изменение кампании и запись события в outbox атомарны. Объём небольшой (тысячи кампаний, единицы изменений в секунду), поэтому масштабирование не горизонтальное, а репликами. PostgreSQL уже знаком команде (TC-5)            |
| **Сервис статистики** (Stats Stream Processor) | **ClickHouse** (колоночная, OLAP) для событий и агрегатов + локальное состояние Kafka Streams (RocksDB) для дедупликации | Поток в десятки тысяч событий в секунду, только добавление, без обновлений. ClickHouse рассчитан на массовую пакетную вставку и сжатие в 5–10 раз; PostgreSQL на таком потоке упирается в WAL, индексы и vacuum — это узкое место AS-IS (B3). Дедупликация в окне 24 ч требует быстрого состояния рядом с обработкой — встроенное хранилище Kafka Streams восстанавливается из changelog-топика |
| **Сервис аналитики** (Reporting Service)       | **ClickHouse** — собственные витрины (отдельная база в общем кластере)                                                   | Отчёты — агрегации по большим объёмам за период: колоночное хранение и materialized views дают ответы за доли секунды. Витрины строятся из событий Kafka (CQRS read model), а не из таблиц Сервиса статистики, поэтому тяжёлые запросы аналитики не мешают записи. Общий кластер с раздельными базами и квотами ресурсов — компромисс по стоимости и эксплуатации                               |
| **Сервис финансов** (Billing Service)          | **PostgreSQL** (реляционная, строгий ACID)                                                                               | Деньги: нужны транзакции, уникальные ограничения для идемпотентности (`source_id` в ledger), внешние ключи, точная арифметика (целые микро-единицы), аудит и PITR-восстановление на момент времени. Синхронная реплика — для RPO = 0. Объём операций умеренный: списания идут агрегатами, а не по каждому показу                                                                                |

### 2.2. Кто владеет какими данными

| Данные                                          | Владелец (источник истины)                        | Где ещё есть копия                        | Как копия обновляется                           |
|:------------------------------------------------|:--------------------------------------------------|:------------------------------------------|:------------------------------------------------|
| Кампании, ставки, таргетинг, креативы           | Сервис кампаний (PostgreSQL)                      | индекс в памяти Сервиса ставок            | `campaign-changes` (outbox) + снимок при старте |
| Сырые события (ставки, выигрыши, показы, клики) | Kafka (3–7 дней) → Сервис статистики (ClickHouse) | витрины Сервиса аналитики                 | Kafka                                           |
| Агрегаты расхода                                | Сервис статистики                                 | Budget & Pacing (Redis), Billing (ledger) | `spend`                                         |
| Остаток и статус бюджета (оперативный)          | Budget & Pacing (Redis)                           | Сервис ставок (память)                    | `budget-status` + запись в Redis                |
| Балансы, списания, счета                        | Сервис финансов (PostgreSQL)                      | —                                         | —                                               |
| Профили и сегменты пользователей                | Redis (оперативно)                                | ClickHouse (история для пересборки)       | обработка событий                               |

### 2.3. Переход от общей БД

1. Этап 1 (3 месяца): общая PostgreSQL остаётся, но получает HA и read replica; события уходят в Kafka и пишутся
   пакетами; Сервис ставок читает только кеш.
2. Этап 2: для каждого выделяемого сервиса — своя схема, затем своя база. Чужие таблицы заменяются API или событиями;
   данные переносятся с параллельной записью и сверкой (особенно финансы).

## 3. Отказоустойчивость данных

### 3.1. RPO и RTO

RPO — сколько данных допустимо потерять (насколько назад откатимся), RTO — за сколько сервис должен восстановиться.

| Сервис            | Сбой узла или зоны: RPO / RTO             | Потеря региона: RPO / RTO          | Как достигается                                                                                                                                      |
|:------------------|:------------------------------------------|:-----------------------------------|:-----------------------------------------------------------------------------------------------------------------------------------------------------|
| Сервис ставок     | не применимо (нет своих данных) / ≤ 2 мин | — / ≤ 5 мин                        | stateless-поды, снимок + Kafka при старте; соседний регион active-active принимает трафик                                                            |
| Сервис кампаний   | 0 / ≤ 1 мин                               | ≤ 1 мин / ≤ 30 мин                 | синхронный standby + автоматическое переключение (Patroni); асинхронная реплика в резервном регионе                                                  |
| Сервис статистики | 0 / ≤ 30 мин                              | 0 / ≤ 2 ч                          | ClickHouse: 2 реплики на шард; любые потерянные данные дочитываются из Kafka (хранение 7 дней)                                                       |
| Сервис аналитики  | 0 / ≤ 1 ч                                 | 0 / ≤ 4 ч                          | витрины пересобираются из событий; некритичный для выручки сервис                                                                                    |
| Сервис финансов   | **0** / ≤ 15 мин                          | ≤ 1 мин, с доведением до 0 / ≤ 1 ч | синхронный standby, архив WAL, PITR; разрыв после потери региона закрывается повторной обработкой `spend` (хранение 30 дней, идемпотентные списания) |
| Budget & Pacing   | секунды / ≤ 5 мин                         | секунды / ≤ 5 мин                  | Redis с репликой и AOF; состояние пересчитывается из `spend` и сверяется с Billing                                                                   |
| Kafka             | 0 для `acks=all` / ≤ 1 мин                | ≤ 1 мин / ≤ 30 мин                 | фактор репликации 3, `min.insync.replicas=2`, зоны доступности; MirrorMaker между регионами                                                          |
| Redis (кеш)       | секунды / ≤ 1 мин                         | — / прогрев ≤ 15 мин               | реплика на каждый шард; данные производные, сервис ставок работает на резервных стратегиях                                                           |

Самые строгие цели — у финансов: потеря денег или двойное списание недопустимы. Самые мягкие — у аналитики: отчёт,
доступный на час позже, не влияет на выручку и SLA с DSP.

### 3.2. Резервное копирование

| Хранилище                     | Что                   | Как и как часто                                                                                                                 | Хранение                                                                               | Восстановление                                                         |
|:------------------------------|:----------------------|:--------------------------------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------|:-----------------------------------------------------------------------|
| PostgreSQL кампаний           | полная копия + WAL    | полная — раз в неделю, инкрементальная — ежедневно, WAL — непрерывно (pgBackRest / WAL-G) в объектное хранилище другого региона | 14 дней PITR, ежемесячные копии — 1 год                                                | на любой момент времени за 14 дней                                     |
| PostgreSQL финансов           | полная копия + WAL    | то же, WAL — непрерывно; дополнительно логическая выгрузка ledger раз в сутки                                                   | 30 дней PITR; ежемесячные копии — по требованиям бухгалтерского учёта (ориентир 5 лет) | на любой момент времени за 30 дней                                     |
| ClickHouse                    | агрегаты и витрины    | ежедневно (clickhouse-backup) в объектное хранилище                                                                             | 30 дней                                                                                | агрегаты — из копии; сырые события за 7 дней — повторным чтением Kafka |
| Kafka                         | — (копии не делаются) | репликация + хранение по времени; резервируются только реестр схем и конфигурация топиков                                       | —                                                                                      | топики пересоздаются из конфигурации как кода                          |
| Redis                         | профили пользователей | RDB-снимок раз в час                                                                                                            | 2 суток                                                                                | загрузка снимка или пересборка из ClickHouse; бюджеты — из `spend`     |
| Объектное хранилище креативов | файлы                 | версионирование + межрегиональная репликация                                                                                    | 30 дней версий                                                                         | восстановление версии                                                  |

Правила:

- копии шифруются и хранятся в другом регионе, доступ — отдельная учётная запись;
- **ежемесячная проверка восстановления** на тестовом стенде с замером фактического RTO: непроверенная копия не
  считается копией;
- алерт, если копия не создана вовремя или отставание архива WAL больше 5 минут.

### 3.3. Соответствие принципам 12-факторных приложений

| Фактор                         | Как соблюдается в работе с данными                                                                                                                                                                                                                                                               |
|:-------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| III. Конфигурация              | адреса БД, Kafka и Redis, логины и пароли — в переменных окружения и секретах Kubernetes, не в коде; разные окружения отличаются только конфигурацией                                                                                                                                            |
| IV. Сторонние службы           | PostgreSQL, ClickHouse, Redis, Kafka — подключаемые ресурсы по адресу; переключение на реплику или другой кластер — смена конфигурации без изменения кода                                                                                                                                        |
| V. Сборка, релиз, выполнение   | миграции схемы входят в релиз и выполняются отдельным шагом до запуска новой версии                                                                                                                                                                                                              |
| VI. Процессы                   | сервисы stateless: всё постоянное состояние — в сторонних службах. Индекс кампаний в памяти Сервиса ставок — кеш, который восстанавливается при старте, а не состояние процесса                                                                                                                  |
| VIII. Параллелизм              | масштабирование добавлением процессов: поды Сервиса ставок по RPS, потребители Kafka — до числа партиций                                                                                                                                                                                         |
| IX. Утилизируемость            | быстрый старт (прогрев с контролем готовности) и корректная остановка: потребитель фиксирует смещение и отдаёт партиции, сервис ставок перестаёт принимать запросы и дорабатывает текущие                                                                                                        |
| X. Паритет окружений           | те же версии PostgreSQL, ClickHouse, Kafka, Redis в разработке (Testcontainers / docker-compose), на тестовом стенде и в продакшене                                                                                                                                                              |
| XI. Журналы                    | логи пишутся в stdout как поток событий и собираются централизованно (Loki), а не в файлы на дисках подов                                                                                                                                                                                        |
| XII. Административные процессы | миграции схем (Flyway / Liquibase), пересборка витрин, переобработка Kafka — разовые задачи (Kubernetes Job) из того же кода и конфигурации. Миграции только обратно совместимые (expand → migrate → contract), чтобы старая и новая версии сервиса работали одновременно во время canary-релиза |
