# Bidding Service: спецификация сервиса ставок

Сервис ставок — первый сервис, выносимый из монолита по стратегии Strangler Fig (ADR-001 задания 1): именно он получает
весь рост трафика от нового партнёра и определяет время ответа. Он объединяет бывшие Ad Server и Auction Engine:
принимает нормализованный запрос на ставку, подбирает рекламу, проводит внутренний аукцион и возвращает ставку или отказ
от ставки в пределах бюджета времени.

Диаграммы:

- `diagrams/component-bidding-service.puml`
- `diagrams/sequence-bid-request.puml`
- `diagrams/sequence-bid-degraded.puml`

## 1. Границы сервиса

### 1.1. Что входит

| Функция                                                                                          | Откуда перенесена               |
|:-------------------------------------------------------------------------------------------------|:--------------------------------|
| Определение пользователя и его сегментов                                                         | Ad Server                       |
| Подбор кандидатов по таргетингу (гео, устройство, формат, сегменты, площадка)                    | Ad Server                       |
| Фильтрация: статус кампании, остаток бюджета, частотные ограничения, минимальная цена (bidfloor) | Ad Server, Auction Engine       |
| Расчёт цены ставки с учётом стратегии кампании и равномерности расхода (pacing)                  | Auction Engine                  |
| Внутренний аукцион: выбор победителя среди кандидатов                                            | Auction Engine                  |
| Сборка ответа: цена, креатив, разметка или ссылка на неё, URL уведомлений о выигрыше и оплате    | Auction Engine + вызов Delivery |
| Публикация результатов аукционов в Kafka                                                         | новая                           |

### 1.2. Что не входит

| Функция                                                                            | Где живёт                                 | Почему вне сервиса                                                              |
|:-----------------------------------------------------------------------------------|:------------------------------------------|:--------------------------------------------------------------------------------|
| Приём OpenRTB, аутентификация партнёров, ограничение частоты, адаптация протоколов | Bid Gateway                               | разные партнёры — разные особенности протокола; ядро аукциона от них не зависит |
| Создание и изменение кампаний, ставок, креативов                                   | Campaign Service                          | источник истины о кампаниях, транзакционная БД                                  |
| Учёт расхода бюджета, pacing-коэффициенты                                          | Budget & Pacing Service                   | учитывает события с задержкой в секунды; аукцион только читает результат        |
| Формирование HTML/JS-разметки                                                      | Delivery Service                          | другой стек и частота изменений                                                 |
| Учёт показов и кликов, списания, счета                                             | Event Collector, Stats Processor, Billing | не нужны для решения о ставке, допускают задержку                               |

**Главный принцип границы:** Bidding Service не владеет ни одной транзакционной БД и не пишет ничего синхронно. Всё
нужное для решения он получает заранее (в память и Redis), а всё, что произошло, публикует в Kafka.

## 2. API

### 2.1. Внешний контракт

Партнёры не обращаются к Bidding Service напрямую. Внешний протокол — OpenRTB 2.6 через API-слой (см. `api-gateway.md`).
Bid Gateway преобразует запрос партнёра во внутренний контракт.

### 2.2. Внутренний контракт (gRPC)

**Методы**

| Метод          | Вход       | Выход       | Кто вызывает      | Назначение                                             |
|:---------------|:-----------|:------------|:------------------|:-------------------------------------------------------|
| `Bid`          | BidRequest | BidResponse | Bid Gateway       | решение о ставке; дедлайн передаётся как gRPC deadline |
| `Health/Check` | —          | статус      | Kubernetes, Envoy | готовность пода (см. 2.3)                              |

**BidRequest — запрос на ставку**

| Поле         | Тип    | Описание                                                                                                      |
|:-------------|:-------|:--------------------------------------------------------------------------------------------------------------|
| `request_id` | строка | id запроса из OpenRTB: трассировка и дедупликация                                                             |
| `partner_id` | строка | DSP-партнёр, определён в Bid Gateway                                                                          |
| `region`     | строка | регион обработки                                                                                              |
| `imps[]`     | список | места под рекламу: `imp_id`, допустимые размеры (w × h), минимальная цена `bidfloor_micros`, требование HTTPS |
| `context`    | объект | площадка: домен сайта или bundle приложения, категории, запрещённые категории и домены рекламодателей         |
| `user`       | объект | идентификатор пользователя, гео (страна, регион, город)                                                       |
| `device`     | объект | тип устройства, ОС, user-agent, хеш IP                                                                        |
| `tmax_ms`    | число  | оставшийся бюджет времени после Bid Gateway                                                                   |
| `currency`   | строка | валюта (ISO 4217)                                                                                             |

**BidResponse — ответ**

| Поле            | Тип          | Описание                                                                                                                           |
|:----------------|:-------------|:-----------------------------------------------------------------------------------------------------------------------------------|
| `request_id`    | строка       | id исходного запроса                                                                                                               |
| `bids[]`        | список       | ставки; пустой список — отказ от ставки                                                                                            |
| `no_bid_reason` | перечисление | причина отказа: нет подходящих кампаний, ниже минимальной цены, бюджет исчерпан, истёк дедлайн, недоступна зависимость, перегрузка |
| `fallback`      | флаги        | какие резервные стратегии сработали: `cached_profile`, `default_price`, `markup_on_win` (см. раздел 8.4)                           |

**Bid — ставка (элемент `bids[]`)**

| Поле                         | Тип    | Описание                                                                      |
|:-----------------------------|:-------|:------------------------------------------------------------------------------|
| `bid_id`                     | UUID   | уникальный id ставки, ключ идемпотентности всех дальнейших событий и списаний |
| `imp_id`                     | строка | на какое место под рекламу ставка                                             |
| `price_micros`               | целое  | цена ставки                                                                   |
| `campaign_id`, `creative_id` | строка | рекламная кампания и баннер-победитель                                        |
| `adm`                        | строка | HTML/JS-разметка баннера; пусто, если разметка отдаётся при выигрыше          |
| `nurl`, `burl`               | строка | подписанные URL уведомлений о выигрыше и об оплате показа                     |
| `adomain`                    | список | домены рекламодателя (партнёр проверяет их по своим блок-листам)              |
| `size`                       | w × h  | размер баннера                                                                |

Деньги везде передаются целыми числами в микро-единицах валюты (`price_micros`), без чисел с плавающей точкой: 1,25
USD = 1 250 000.

### 2.3. Служебные эндпоинты

| Эндпоинт                      | Назначение                                                                                                   |
|:------------------------------|:-------------------------------------------------------------------------------------------------------------|
| `grpc.health.v1.Health/Check` | liveness и readiness; readiness = true только после загрузки снимка кампаний и при отставании индекса ≤ 30 с |

## 3. Зависимости

| Зависимость                                | Тип                             | Когда используется          | Таймаут       | Если недоступна                                                       |
|:-------------------------------------------|:--------------------------------|:----------------------------|:--------------|:----------------------------------------------------------------------|
| In-memory индекс кампаний                  | локально                        | каждый запрос               | —             | — (часть сервиса)                                                     |
| Redis: профили пользователей               | синхронно                       | каждый запрос               | 5 мс          | резервная стратегия: таргетинг только по контексту                    |
| Redis: статус бюджета, частота показов     | синхронно (pipeline с профилем) | каждый запрос               | 5 мс          | последний известный статус из памяти + консервативный pacing          |
| Delivery Service                           | gRPC                            | только для победителя       | 10 мс         | разметка по win notice (`markup_on_win`)                              |
| Kafka: `campaign-changes`, `budget-status` | асинхронно, чтение              | постоянно в фоне            | —             | работа на последнем снимке; при отставании > 30 с — readiness = false |
| Campaign Service: снимок кампаний          | gRPC stream                     | при старте и восстановлении | 60 с          | под не переходит в ready и не получает трафик                         |
| Kafka: `bids`                              | асинхронно, запись              | после ответа                | неблокирующая | локальный буфер; при переполнении события отбрасываются с метрикой    |

Ни одна из зависимостей не обращается к SQL-базе в момент обработки запроса.

## 4. Модель данных

### 4.1. In-memory индекс кампаний

Загружается снимком из Campaign Service при старте и обновляется событиями `campaign-changes`.

| Сущность       | Поля                                                                                                                                                                                                                                                    |
|:---------------|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Campaign       | `campaign_id`, `advertiser_id`, `status` (active / paused / budget_exhausted), `bid_strategy` (CPM / CPC), `max_bid_micros`, `default_bid_micros`, `daily_budget_micros`, `freq_cap` (показов на пользователя в сутки), `start_at`, `end_at`, `version` |
| TargetingRules | `campaign_id`, `geo[]`, `device_types[]`, `os[]`, `segments_include[]`, `segments_exclude[]`, `categories_include[]`, `domains_block[]`, `schedule` (часы и дни недели)                                                                                 |
| Creative       | `creative_id`, `campaign_id`, `size` (w × h), `format`, `template_id`, `adomain`, `category`, `status`                                                                                                                                                  |

Индексы для быстрого подбора (инвертированные): `size → creatives`, `country → campaigns`, `device_type → campaigns`,
`segment → campaigns`. Подбор — пересечение множеств, без перебора всех кампаний.

Обновления применяются по `version`: событие с версией меньше текущей игнорируется (защита от повторов и перестановок
событий).

### 4.2. Redis

| Ключ                           | Тип     | Содержимое                                   | TTL     | Кто пишет                         |
|:-------------------------------|:--------|:---------------------------------------------|:--------|:----------------------------------|
| `user:{user_id}`               | hash    | сегменты, гео по умолчанию, время обновления | 30 дней | сервис профилей / Stats Processor |
| `budget:status:{campaign_id}`  | string  | `ok` / `throttled` / `exhausted`             | 1 сутки | Budget & Pacing                   |
| `pacing:{campaign_id}`         | string  | коэффициент участия 0–1                      | 10 мин  | Budget & Pacing                   |
| `freq:{user_id}:{campaign_id}` | integer | число показов за сутки                       | 24 ч    | Stats Processor                   |

Все чтения на запрос выполняются одним pipeline-вызовом.

### 4.3. Событие `bids` (Kafka)

| Поле                         | Тип               | Описание                                   |
|:-----------------------------|:------------------|:-------------------------------------------|
| `bid_id`                     | UUID              | уникальный id ставки, ключ идемпотентности |
| `request_id`                 | string            | id запроса партнёра                        |
| `partner_id`                 | string            | DSP-партнёр                                |
| `imp_id`                     | string            |                                            |
| `campaign_id`, `creative_id` | string            | ключ партиции — `campaign_id`              |
| `price_micros`               | int64             | цена ставки                                |
| `outcome`                    | enum              | `bid` / `no_bid`                           |
| `no_bid_reason`              | enum              |                                            |
| `fallback`                   | flags             | какие резервные стратегии сработали        |
| `latency_ms`                 | int               | время обработки                            |
| `region`, `ts`               | string, timestamp |                                            |

Формат — Protobuf, схемы в Schema Registry; изменения только обратно совместимые (новые поля опциональны).

### 4.4. Данные, которыми сервис не владеет

Кампании, креативы, бюджеты и финансы хранятся в Campaign DB и Billing DB. Bidding Service хранит только их производную
копию для чтения и может восстановить её с нуля из снимка и событий.

## 5. Обработка запроса и бюджет времени

| Шаг | Что происходит                                                                          | Бюджет, мс  |
|:----|:----------------------------------------------------------------------------------------|:------------|
| 1   | Проверка дедлайна: если `tmax_ms` < 15 — сразу no-bid `DEADLINE_EXCEEDED`               | < 1         |
| 2   | Redis pipeline: профиль, статус бюджета, pacing, частота                                | 1–3         |
| 3   | Подбор кандидатов по инвертированным индексам                                           | 3–8         |
| 4   | Фильтрация: статус, бюджет, частота, bidfloor, блок-листы площадки                      | 1–3         |
| 5   | Расчёт цены: `min(max_bid, base_bid × pacing × коэффициент качества)`, не ниже bidfloor | 1–3         |
| 6   | Внутренний аукцион: победитель по максимальной ожидаемой стоимости показа (eCPM)        | < 1         |
| 7   | Разметка победителя через Delivery Service                                              | 3–8         |
| 8   | Ответ; событие в Kafka отправляется асинхронно после ответа                             | < 1         |
|     | **Итого внутри сервиса**                                                                | **≤ 25–35** |

На каждом шаге сервис проверяет остаток дедлайна. Если времени не хватает на следующий шаг — возвращает лучший
результат, который уже есть (например, без вызова Delivery — с `markup_on_win`), или no-bid.

## 6. Масштабирование и развёртывание

- **Stateless.** Любой под обслуживает любой запрос; состояние — копия индекса в памяти.
- **Горизонтальное масштабирование:** Kubernetes HPA по RPS на под и CPU (цель 60%), минимум N+2 пода в регионе.
- **Оценка мощности** (уточняется нагрузочным тестом): ~1 500 RPS на под при P95 ≤ 30 мс → для 18 000 RPS — 12 подов + 2
  резервных; для 50 000 RPS на два региона — по ~20 подов в регионе.
- **Прогрев:** под получает трафик только после загрузки снимка и догона событий (readiness).
- **Релизы:** canary 5% → 25% → 100% с автоматическим откатом при росте P95 или доли ошибок.

## 7. SLO и метрики

| Метрика                                                       | Цель                        |
|:--------------------------------------------------------------|:----------------------------|
| Время обработки в сервисе, P95 / P99                          | ≤ 30 мс / ≤ 45 мс           |
| Доля ответов с ошибкой (не no-bid)                            | < 0,1%                      |
| Доля no-bid по `DEADLINE_EXCEEDED` и `DEPENDENCY_UNAVAILABLE` | < 1%                        |
| Отставание индекса кампаний от событий                        | ≤ 5 с (алерт > 30 с)        |
| Доля ответов с резервными стратегиями                         | наблюдается; алерт при > 5% |

Все метрики — с разрезом по партнёру и региону.

## 8. Паттерны надёжности

### 8.1. Circuit Breaker для зависимых сервисов

Размыкатель стоит на каждой синхронной зависимости внутри сервиса (Redis, Delivery) и на вызове Bidding Service со
стороны Bid Gateway (см. `api-gateway.md`).

| Параметр               | Redis                                     | Delivery Service                          |
|:-----------------------|:------------------------------------------|:------------------------------------------|
| Окно оценки            | 10 с, минимум 200 вызовов                 | 10 с, минимум 100 вызовов                 |
| Условие размыкания     | ≥ 30% ошибок или таймаутов                | ≥ 30% ошибок или таймаутов                |
| Время в состоянии open | 5 с                                       | 10 с                                      |
| Half-open              | 5% запросов идут в зависимость            | 5% запросов                               |
| Поведение в open       | резервная стратегия без ожидания таймаута | резервная стратегия без ожидания таймаута |

Смысл: при деградации зависимости не тратить на каждый запрос полный таймаут, а сразу переходить на резервный вариант и
сохранить бюджет времени.

### 8.2. Повторные попытки с экспоненциальной задержкой

**В hot path повторов нет.** Бюджет времени 80 мс не позволяет повторить вызов: повтор почти гарантированно приводит к
опозданию, а опоздание штрафуется сильнее, чем отказ от ставки. Вместо повтора — резервная стратегия.

Повторы применяются там, где нет жёсткого дедлайна:

| Где                                       | Политика                                                                           |
|:------------------------------------------|:-----------------------------------------------------------------------------------|
| Загрузка снимка кампаний при старте       | 100 мс × 2ⁿ, максимум 10 с, jitter ±20%, до готовности                             |
| Kafka-продюсер (`bids`)                   | встроенные повторы продюсера, `retry.backoff.ms` с ростом, идемпотентный продюсер  |
| Kafka-консьюмеры (Stats, Budget, Billing) | 200 мс × 2ⁿ, максимум 30 с, jitter; после 5 неудач — сообщение в DLQ-топик и алерт |
| Billing → платёжный шлюз                  | 1 с × 2ⁿ, максимум 5 мин, jitter, с ключом идемпотентности                         |

Jitter (случайный разброс задержки) обязателен: без него после сбоя все клиенты повторяют одновременно и снова
перегружают зависимость.

### 8.3. Идемпотентность финансовых операций

Деньги связаны с событиями, которые могут прийти повторно: партнёр повторяет win notice, Kafka доставляет at-least-once,
консьюмер перечитывает после сбоя.

| Звено                            | Ключ идемпотентности                           | Механизм                                                                                                                             |
|:---------------------------------|:-----------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------|
| Ставка                           | `bid_id` (UUID, создаётся в Bidding Service)   | один `bid_id` — максимум одно списание                                                                                               |
| Win notice / billing notice      | `bid_id` в подписанном `nurl` / `burl`         | Event Collector проверяет подпись; повторное уведомление с тем же `bid_id` не создаёт новое событие (дедупликация в Redis, TTL 24 ч) |
| Показы и клики в Stats Processor | `event_id`                                     | дедупликация в окне 24 ч (состояние потоковой обработки)                                                                             |
| Агрегат расхода `spend`          | `campaign_id` + номер окна агрегации           | детерминированный id агрегата                                                                                                        |
| Ledger в Billing                 | уникальный индекс по `source_id` (id агрегата) | повторная запись — нарушение уникальности, транзакция не создаётся, возвращается прежний результат                                   |
| Платёжный шлюз                   | `Idempotency-Key` в запросе                    | шлюз возвращает результат первой операции                                                                                            |

Kafka-продюсеры работают с `enable.idempotence=true`, консьюмеры фиксируют смещение только после записи результата.

### 8.4. Резервные стратегии

Порядок деградации — от наименее заметной к крайней мере:

| Ситуация                                                  | Резервная стратегия                                                                                                                                                              | Флаг в ответе    |
|:----------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-----------------|
| Профиль пользователя недоступен (Redis тормозит, CB open) | таргетинг только по контексту: площадка, гео по IP, устройство; кампании с обязательными сегментами пропускаются                                                                 | `cached_profile` |
| Pacing или статус бюджета недоступен                      | последний известный статус из памяти (обновляется событиями `budget-status`); для кампаний с остатком < 10% — no-bid; цена = `default_bid_micros` кампании (ставка по умолчанию) | `default_price`  |
| Delivery Service недоступен                               | ставка без `adm`: разметка отдаётся по `nurl` при выигрыше (OpenRTB допускает такой режим); если партнёр его не поддерживает — шаблонная разметка из кеша Bid Gateway            | `markup_on_win`  |
| Индекс кампаний устарел > 30 с                            | под выводится из балансировки (readiness = false), трафик уходит на другие поды                                                                                                  | —                |
| Дедлайн почти исчерпан или под перегружен                 | no-bid с причиной `DEADLINE_EXCEEDED` / `OVERLOADED`                                                                                                                             | —                |

Ни одна резервная стратегия не увеличивает время ответа: все они срабатывают быстрее, чем ожидание недоступной
зависимости.

## 9. Вынос из монолита

1. Код Ad Server и Auction Engine переносится в отдельный сервис; прямые SQL-запросы заменяются чтением из индекса и
   Redis.
2. **Shadow-режим:** Edge Proxy дублирует копию трафика в новый сервис, ответы сравниваются с монолитом, партнёру уходит
   ответ монолита. Критерий — расхождение победителей < 0,1%.
3. **Canary:** 5% → 25% → 100% реального трафика с автоматическим откатом.
4. Код аукциона в монолите удаляется после двух недель стабильной работы на 100%.
