# AdScale: RTB-сервис и интеграция с DSP

## Задача

Спроектировать критичный компонент платформы — RTB-сервис для интеграции с новой DSP-площадкой — так, чтобы при 18 000
RPS (через год — 50 000 RPS) ответ партнёру стабильно укладывался в 80 мс, а сбои зависимостей не приводили к
опозданиям, штрафам и ошибкам в деньгах.

Работа продолжает задание 1: стратегия миграции — Strangler Fig (ADR-001), первым из монолита выносится Bidding Service,
события идут через Kafka (TO-BE.md задания 1).

## Ключевые решения

1. **Bidding Service** объединяет бывшие Ad Server и Auction Engine, не владеет транзакционной БД и не пишет ничего
   синхронно. Данные кампаний держит в памяти (снимок при старте + события `campaign-changes`), профили и статус бюджета
   читает из Redis одним pipeline-вызовом, результаты публикует в Kafka после ответа.
2. **Протоколы:**
    - снаружи — OpenRTB 2.6 по HTTPS, отказ от ставки — HTTP 204;
    - внутри hot path — gRPC: компактный Protobuf, HTTP/2, дедлайны передаются по цепочке;
    - данные кампаний — события Kafka (outbox), а не синхронный вызов Campaign Service на каждый запрос;
    - показы и клики — Kafka (`acks=all`, идемпотентность), кабинет — REST.
3. **API-слой для DSP = Envoy + Bid Gateway (Go)**, отдельно от шлюза кабинета (Kong): mTLS и RBAC по партнёру,
   локальный rate limiting без внешних вызовов, adaptive concurrency, защита от перегрузки в Envoy (отказ — 204, а не
    503) и Circuit Breaker перед Bidding Service, взвешенная маршрутизация для canary и Strangler Fig, метрики задержки
         по партнёру.
4. **Надёжность:**
    - Circuit Breaker на Redis, Delivery и Bidding Service;
    - повторы с экспоненциальной задержкой и jitter — только вне hot path (в бюджет 80 мс повтор не помещается);
    - идемпотентность денег по цепочке `bid_id` → `event_id` → `spend_id` → уникальный ключ в ledger;
    - резервные стратегии: контекстный таргетинг, статус бюджета из памяти, ставка по умолчанию, разметка по win notice,
      кешированная ставка, no-bid.

## Уточнения относительно задания 1

- Добавлен топик `wins` (уведомления о выигрыше) — отдельно от показов, потому что у партнёров оплата может идти за
  выигрыш или за показ.
- Bidding Service читает статус бюджета и из Redis, и из событий `budget-status` в памяти: второе — резерв при
  недоступности Redis.
