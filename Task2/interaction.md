| 6  | Campaign Service → Kafka `campaign-changes` → Bidding Service                      | Kafka, transactional outbox                     | событийная репликация данных                         | изменения кампаний, ставок, креативов         |

| 9  | DSP / браузер → Event Collector                                                    | HTTPS GET (подписанные `nurl`, `burl`, пиксели) | синхронный приём, асинхронная обработка              | уведомления о выигрыше, оплате, показы, клики |
| 10 | Event Collector → Kafka `impressions`, `clicks`, `wins`                            | Kafka                                           | асинхронная публикация, `acks=all`                   | события, влияющие на деньги                   |

| 12 | Advertiser Dashboard → API Gateway (кабинет) → Campaign / Billing / Reporting      | HTTPS REST (JSON)                               | синхронный запрос-ответ                              | управление кампаниями, отчёты                 |

## 2. Внешний протокол с DSP: OpenRTB 2.6

**Почему OpenRTB:** отраслевой стандарт RTB, его поддерживают все крупные DSP и SSP. Собственный протокол потребовал бы
доработок у партнёра и замедлил бы интеграцию; поддержка стандарта упрощает подключение следующих платформ
(мультиплатформенная интеграция в целевом решении).

Параметры интеграции:

| Параметр        | Значение                                                                              |
|:----------------|:--------------------------------------------------------------------------------------|
| Транспорт       | HTTPS, HTTP/2 или HTTP/1.1 с keep-alive (без нового TLS-рукопожатия на каждый запрос) |
| Формат          | JSON, сжатие gzip; Protobuf-вариант OpenRTB — если партнёр поддерживает               |
| Эндпоинт        | `POST /openrtb/2.6/{partner_id}/bid`                                                  |
| Тайм-аут        | `tmax` из запроса, но не больше договорных 80 мс                                      |
| Отказ от ставки | HTTP 204 без тела (принято в OpenRTB, не считается ошибкой)                           |
| Уведомления     | `nurl` — о выигрыше, `burl` — об оплате показа; подписаны HMAC                        |
| Аутентификация  | mTLS + список разрешённых IP (подробнее в `api-gateway.md`)                           |

## 3. Внутреннее синхронное взаимодействие: gRPC или REST

### 3.1. Сравнение для hot path

| Критерий                  | gRPC                                                                                        | REST (JSON / HTTP)                                          |
|:--------------------------|:--------------------------------------------------------------------------------------------|:------------------------------------------------------------|
| Размер и разбор сообщений | Protobuf: компактно, разбор быстрее JSON в несколько раз                                    | JSON: больше объём, дороже разбор                           |
| Соединения                | HTTP/2: мультиплексирование, одно долгоживущее соединение                                   | HTTP/1.1: пул соединений, head-of-line blocking             |
| Дедлайны                  | встроены: дедлайн передаётся по цепочке вызовов, вызываемая сторона видит, сколько осталось | нет стандарта, нужно передавать заголовком вручную          |
| Контракт                  | строгий, генерация клиентов на C++, Go, Node.js, Python                                     | OpenAPI, но без строгой проверки типов на уровне транспорта |
| Отладка и браузеры        | нужны специальные инструменты                                                               | проще, работает из браузера                                 |

### 3.2. Решение

- **Bid Gateway → Bidding Service, Bidding Service → Delivery Service: gRPC.** Каждая миллисекунда на счету, а дедлайны
  должны передаваться по цепочке. Стек сервисов разный (Go, C++, Node.js) — Protobuf даёт один контракт для всех.
- **Bidding Service ↔ Campaign Service: не синхронный вызов на каждый запрос, а события + gRPC-снимок при старте.**
    - Синхронный вызов Campaign Service на каждый bid-request вернул бы базу данных в hot path — ровно ту проблему,
      которую мы устраняем.
    - Данные кампаний меняются редко (единицы изменений в секунду) и читаются 18 000–50 000 раз в секунду — их выгодно
      держать копией в памяти Bidding Service.
    - Изменения доставляются через Kafka `campaign-changes` (outbox гарантирует, что событие публикуется тогда и только
      тогда, когда изменение сохранено в БД).
    - При старте под получает полный снимок через gRPC server streaming: это одна долгая операция с большим объёмом
      данных — стриминг gRPC подходит для неё лучше, чем постраничный REST.
- **Кабинет рекламодателя → back-office-сервисы: REST.** Это интерактивный трафик без жёстких требований к
  миллисекундам; REST проще для фронтенда, публичного API и интеграций клиентов.

## 4. Потоковая обработка событий: Kafka

### 4.1. Почему Kafka для показов и кликов

| Требование                                               | Как закрывает Kafka                                                                                     |
|:---------------------------------------------------------|:--------------------------------------------------------------------------------------------------------|
| Объём: десятки тысяч событий в секунду с ростом в 3 раза | горизонтальное масштабирование партициями                                                               |
| Не мешать hot path                                       | публикация асинхронная, продюсер отвечает за миллисекунды; запись в хранилище — пакетами в другом месте |
| Не терять события, которые превращаются в деньги         | журнал с репликацией (`acks=all`, `min.insync.replicas=2`), хранение 7 дней, перечитывание после сбоя   |
| Несколько потребителей одного потока                     | consumer groups: статистика, бюджет, биллинг, аналитика читают независимо                               |
| Порядок в рамках кампании                                | ключ партиции = `campaign_id`                                                                           |

Синхронная запись событий (REST или gRPC в сервис статистики) вернула бы прямую зависимость hot path от скорости
хранилища.

Альтернативы брокеру Kafka и почему они не выбраны:

- **RabbitMQ** — сообщение удаляется после подтверждения, поток нельзя перечитать после сбоя; на каждого потребителя
  нужна своя очередь, что при таком объёме дорого.
- **Redis Streams** — хранение ограничено памятью, нет штатной межрегиональной репликации; Redis уже используется как
  кеш, смешивать роли рискованно.
- **NATS JetStream, Apache Pulsar** — технически подходят, но у них меньше управляемых сервисов и специалистов на рынке,
  а в команде нет SRE.

### 4.2. Топики

| Топик              | Продюсер                  | Ключ          | Партиций (старт) | `acks` | Хранение  | Потребители                       |
|:-------------------|:--------------------------|:--------------|:-----------------|:-------|:----------|:----------------------------------|
| `bids`             | Bidding Service           | `campaign_id` | 48               | 1      | 3 дня     | Stats Processor                   |
| `wins`             | Event Collector           | `campaign_id` | 24               | all    | 7 дней    | Stats Processor                   |
| `impressions`      | Event Collector           | `campaign_id` | 48               | all    | 7 дней    | Stats Processor                   |
| `clicks`           | Event Collector           | `campaign_id` | 12               | all    | 7 дней    | Stats Processor                   |
| `spend`            | Stats Processor           | `campaign_id` | 12               | all    | 30 дней   | Budget & Pacing, Billing          |
| `budget-status`    | Budget & Pacing           | `campaign_id` | 6                | all    | compacted | Bidding Service, Campaign Service |
| `campaign-changes` | Campaign Service (outbox) | `campaign_id` | 6                | all    | compacted | Bidding Service                   |

- `bids` — аналитический поток: допускается редкая потеря при сбое брокера ради минимальной задержки (`acks=1`).
- `wins`, `impressions`, `clicks`, `spend` — денежные потоки: `acks=all`, идемпотентный продюсер.
- `budget-status`, `campaign-changes` — compacted-топики: хранится последнее состояние по ключу, новый потребитель может
  восстановить полное состояние.

### 4.3. Гарантии доставки

- **At-least-once + идемпотентные потребители.** Exactly-once между разными системами (Kafka → ClickHouse → PostgreSQL)
  недостижим без распределённых транзакций, поэтому дубликаты устраняются ключами идемпотентности (`bid_id`, `event_id`,
  id агрегата), см. `bidding-service.md`, раздел 8.3.
- **Схемы событий** — Protobuf в Schema Registry, только обратно совместимые изменения.
- **Ошибки обработки** — повторы с экспоненциальной задержкой, затем DLQ-топик `<topic>.dlq` и алерт.

## 5. Нужен ли API Gateway

**Да, но два разных — по классу трафика.**

|                       | Трафик DSP (RTB)                                                                    | Трафик кабинета и публичного API                            |
|:----------------------|:------------------------------------------------------------------------------------|:------------------------------------------------------------|
| Объём                 | 18 000 → 50 000 RPS                                                                 | сотни RPS                                                   |
| Требование ко времени | ≤ 80 мс на весь ответ, на шлюз — ≤ 5 мс                                             | сотни миллисекунд допустимы                                 |
| Аутентификация        | партнёры: mTLS, IP                                                                  | пользователи: OAuth 2.0 / OIDC, JWT                         |
| Функции               | rate limiting по партнёрам, дедлайны, размыкатели, load shedding, адаптация OpenRTB | маршрутизация к сервисам, аутентификация, квоты, версии API |
| Решение               | **Envoy + Bid Gateway (Go)**                                                        | **Kong** (на Envoy-совместимой или собственной основе)      |

**Почему не один шлюз на всё:**

- Плагины универсального шлюза (Kong на Lua, авторизация через внешние вызовы) добавляют миллисекунды, которых в RTB
  нет.
- Разная критичность: пик отчётов в кабинете не должен влиять на ставки (изоляция отказов).
- Разные требования к развёртыванию: RTB-шлюз — в каждом регионе active-active, шлюз кабинета — в основном регионе.

**Почему Envoy для RTB:**

- Высокая производительность (C++), задержка прокси — доли миллисекунды.
- Встроенные функции, нужные по заданию: локальный rate limiting, circuit breakers, outlier detection, таймауты,
  взвешенная маршрутизация (canary и Strangler Fig), метрики по перцентилям, OpenTelemetry.
- Уже используется как Edge Proxy на этапе 1 — команда не осваивает второй прокси.

Логика, которой нет в Envoy (разбор OpenRTB, особенности партнёров, нормализация, резервные ответы), вынесена в лёгкий
сервис **Bid Gateway** на Go. Дизайн — в `api-gateway.md`.
