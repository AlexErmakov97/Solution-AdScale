# API Gateway для интеграции с DSP

API-слой для RTB-трафика состоит из двух частей:

- **Envoy** — L7-прокси на входе: TLS и mTLS, маршрутизация, ограничение частоты, размыкатели, outlier detection,
  метрики;
- **Bid Gateway** (Go) — прикладная часть: разбор и проверка OpenRTB, адаптеры под партнёров, дедлайны, вызов Bidding
  Service, резервные ответы.

Диаграммы: `diagrams/component-api-gateway.puml`, `diagrams/sequence-bid-request.puml`,
`diagrams/sequence-bid-degraded.puml`.

## 1. Требования

| Требование                | Значение                                                       |
|:--------------------------|:---------------------------------------------------------------|
| Пропускная способность    | 18 000 RPS (этап 1), 50 000 RPS (через год), запас 30% на пики |
| Собственная задержка слоя | P99 ≤ 5 мс (Envoy + Bid Gateway без учёта Bidding Service)     |
| Ответ партнёру            | стабильно ≤ 80 мс; ответ после `tmax` не отправляется          |
| Доступность               | 99.9%; отказ одного пода или зоны не заметен партнёру          |
| Изоляция партнёров        | всплеск трафика одного DSP не ухудшает обслуживание других     |

## 2. Архитектура слоя

```
DSP ──HTTPS──▶ Global LB (GeoDNS, L4/L7) ──▶ Envoy (N подов на регион)
                                                │  TLS/mTLS, RBAC, local rate limit,
                                                │  adaptive concurrency, timeouts, метрики
                                                ▼
                                         Bid Gateway (Go, N подов)
                                                │  адаптер партнёра, валидация OpenRTB,
                                                │  дедлайн, circuit breaker, резервный ответ
                                                ▼ gRPC
                                         Bidding Service
```

- Envoy и Bid Gateway разворачиваются в каждом регионе, stateless, масштабируются HPA.
- Envoy работает как отдельный пул подов (edge), а не sidecar: так проще управлять TLS и лимитами партнёров в одном
  месте.

## 3. Маршрутизация запросов на ставки

### 3.1. Эндпоинты

| Метод и путь                         | Назначение                            | Куда            |
|:-------------------------------------|:--------------------------------------|:----------------|
| `POST /openrtb/2.6/{partner_id}/bid` | запрос на ставку                      | Bid Gateway     |
| `GET /rtb/win?...&sig=...`           | уведомление о выигрыше (`nurl`)       | Event Collector |
| `GET /rtb/bill?...&sig=...`          | уведомление об оплате показа (`burl`) | Event Collector |
| `GET /healthz`                       | проверка доступности для Global LB    | Envoy           |

### 3.2. Правила

1. **По партнёру.** `partner_id` в пути сверяется с идентификатором из клиентского сертификата (см. раздел 4).
   Несовпадение — 403.
2. **По версии протокола.** Путь содержит версию OpenRTB; Bid Gateway выбирает адаптер `partner_id + версия`.
3. **По региону.** Global LB направляет партнёра в ближайший здоровый регион; внутри региона Envoy балансирует по Bid
   Gateway алгоритмом least request.
4. **Strangler Fig (этап 1).** Взвешенные кластеры Envoy: `monolith` и `bidding-service`. Вес меняется без перезапуска:
   0% (shadow через `request_mirror_policy`) → 5% → 25% → 100%. Откат — возврат веса.

```yaml
# Фрагмент маршрута Envoy (этап 1): canary-переключение с монолита на новый сервис
route:
  timeout: 75ms                  # общий потолок, внутри — дедлайн по tmax
  weighted_clusters:
    clusters:
      - name: bid_gateway        # новый путь: Bid Gateway → Bidding Service
        weight: 25
      - name: monolith_ad_server
        weight: 75
  request_mirror_policies: # shadow-режим до начала canary
    - cluster: bid_gateway_shadow
      runtime_fraction: { default_value: { numerator: 0 } }
```

## 4. Аутентификация

| Механизм                                                                             | Где                                               | Зачем                                                                                        |
|:-------------------------------------------------------------------------------------|:--------------------------------------------------|:---------------------------------------------------------------------------------------------|
| **mTLS** — у каждого партнёра свой клиентский сертификат, `partner_id` записан в SAN | Envoy (`require_client_certificate`, RBAC по SAN) | криптографически надёжная идентификация без дополнительного сетевого вызова на каждый запрос |
| **Список разрешённых IP** партнёра                                                   | Envoy (RBAC)                                      | второй фактор, защита при утечке сертификата                                                 |
| **API-ключ** в заголовке `X-Partner-Key`                                             | Bid Gateway (сравнение с хешем в памяти)          | только для партнёров, не поддерживающих mTLS                                                 |
| **Подпись HMAC** в `nurl` и `burl` (`bid_id`, цена, время, `sig`)                    | Event Collector                                   | защита от поддельных уведомлений о выигрыше и оплате (на них завязаны деньги)                |

Внешний сервис авторизации (`ext_authz`) на hot path не используется: лишний сетевой вызов на каждый запрос.
Сертификаты, IP и ключи загружаются в память при старте и обновляются через конфигурацию (SDS) без перезапуска.

## 5. Ограничение частоты запросов

### 5.1. Квоты

Квоты закрепляются в договоре с партнёром. Пример для нового DSP: +20% к текущим 15 000 RPS = **3 000 RPS** базово,
всплески до **3 600 RPS**.

### 5.2. Реализация

- **Локальный token bucket в каждом поде Envoy** (`local_ratelimit`): квота пода = квота партнёра / число подов в
  регионе. Решение принимается в памяти, без обращения к внешнему сервису лимитов — ноль добавленной задержки.
- **Глобальный сервис лимитов** (Envoy RLS + Redis) — только для низкочастотных эндпоинтов (`win`, `bill`) и
  административных лимитов, где лишняя миллисекунда не критична.
- **Ответ при превышении — HTTP 204 (no-bid), а не 429.** Для DSP это штатный отказ от ставки, который не считается
  ошибкой и не штрафуется, а 429 может засчитываться как сбой.

### 5.3. Защита от перегрузки (load shedding)

Rate limiting защищает от превышения договора, а load shedding — от перегрузки самой системы:

- **Adaptive concurrency** в Envoy: при росте задержки до Bid Gateway автоматически снижается число одновременных
  запросов, лишние сразу получают 204.
- **Приоритеты:** при перегрузке первыми отбрасываются запросы с низкой минимальной ценой (`bidfloor`) и от партнёров
  без штрафных SLA.
- **Ранний отказ:** если `tmax` запроса меньше 20 мс, Bid Gateway сразу отвечает 204 — успеть всё равно нельзя.

## 6. Circuit Breaker и защита от перегрузки

Защита работает на двух уровнях с разными задачами:

|                   | 6.1. Envoy → Bid Gateway                                                   | 6.2. Bid Gateway → Bidding Service                      |
|:------------------|:---------------------------------------------------------------------------|:--------------------------------------------------------|
| Что защищает      | от перегрузки очередью и от отдельных сбойных подов Bid Gateway            | от деградации всего сервиса ставок                      |
| Механизм          | лимиты соединений и очереди + исключение сбойных подов (outlier detection) | классический Circuit Breaker: closed → open → half-open |
| Знает про OpenRTB | нет                                                                        | да: отвечает 204 или кешированной ставкой               |

Классическим размыкателем является только уровень 6.2. Уровень 6.1 — инфраструктурная защита Envoy (в его конфигурации
она называется `circuit_breakers`, но по смыслу это лимиты).

### 6.1. Защита от перегрузки и исключение сбойных подов (Envoy → Bid Gateway)

**Зачем:**

- **Лимиты соединений и очереди.** Если поды Bid Gateway замедлились (пауза сборщика мусора, всплеск трафика), без
  лимита Envoy продолжит копить запросы в очереди — каждый дождётся таймаута, и опоздают все запросы, а не часть. С
  лимитом лишние запросы сразу получают отказ, остальные обслуживаются вовремя.
- **Outlier detection.** Под с подряд идущими ошибками или таймаутами временно исключается из балансировки, иначе один
  сбойный под из десяти портит 10% ответов.

**Отказ — это 204, а не 503.** По умолчанию при переполнении лимита, отсутствии здоровых подов или таймауте Envoy
отвечает 503, а для DSP это ошибка, которая может штрафоваться.

### 6.2. Circuit Breaker: Bid Gateway → Bidding Service

| Параметр   | Значение                                                       |
|:-----------|:---------------------------------------------------------------|
| Окно       | скользящее, 10 с, минимум 200 вызовов                          |
| Размыкание | ≥ 20% ошибок или превышений дедлайна                           |
| Open       | 5 с: все запросы сразу получают 204 без вызова Bidding Service |
| Half-open  | 5% запросов идут в Bidding Service; при успехе ≥ 95% — closed  |
| Разрез     | отдельный размыкатель на регион и на версию (canary)           |

**Почему так:** при деградации Bidding Service каждый запрос иначе ждал бы полный дедлайн и отвечал бы партнёру с
опозданием — это и штраф, и рост нагрузки. Быстрый отказ 204 сохраняет время ответа в норме и даёт сервису
восстановиться.

### 6.3. Резервный ответ при открытом размыкателе

1. **По умолчанию — no-bid (204):** безопасно, не штрафуется.
2. **Опционально — кешированная ставка:** для типовых запросов (размер, площадка, гео) Bid Gateway хранит в памяти
   последнюю выигравшую ставку с TTL 60 с и отвечает ею, если кампания ещё активна по последнему `budget-status`.
   Включается флагом для партнёра, когда потеря выручки от no-bid больше риска неточной ставки.

## 7. Дедлайны и таймауты

| Уровень                   | Значение                                                                               |
|:--------------------------|:---------------------------------------------------------------------------------------|
| Ответ партнёру            | `min(tmax, 80 мс)`                                                                     |
| Запас на сеть до партнёра | 10–15 мс (настраивается по партнёру по замерам RTT)                                    |
| Дедлайн Bidding Service   | `min(tmax, 80) − запас − время, уже потраченное в шлюзе`; передаётся как gRPC deadline |
| Если дедлайн истёк        | 204, gRPC-вызов отменяется                                                             |
| Повторы                   | **нет**: в бюджет 80 мс повтор не помещается                                           |

## 8. Мониторинг времени отклика

### 8.1. Метрики

| Метрика                                                 | Разрез                           | Источник                     |
|:--------------------------------------------------------|:---------------------------------|:-----------------------------|
| Время ответа партнёру (гистограмма: P50, P95, P99, max) | партнёр, регион, маршрут, версия | Envoy                        |
| Время Bid Gateway и Bidding Service отдельно            | партнёр, регион                  | Bid Gateway, Bidding Service |
| Доля ответов после `tmax` (опоздания)                   | партнёр                          | Bid Gateway                  |
| Доля no-bid по причинам                                 | партнёр, причина                 | Bid Gateway, Bidding Service |
| Отклонено по rate limit и load shedding                 | партнёр                          | Envoy                        |
| Состояние размыкателей, исключённые поды                | регион                           | Envoy, Bid Gateway           |
| RPS и ошибки 5xx                                        | партнёр, регион                  | Envoy                        |

### 8.2. SLO и алерты

| SLO                                                        | Цель                    | Алерт                                                                                                     |
|:-----------------------------------------------------------|:------------------------|:----------------------------------------------------------------------------------------------------------|
| Ответ партнёру ≤ 80 мс (P95 ≤ 80 мс, Drivers.md задания 1) | 95% запросов за 30 дней | burn rate: расход бюджета ошибок в 14 раз быстрее нормы за 1 ч — срочно; в 6 раз за 6 ч — в рабочее время |
| Внутренняя цель с запасом: P95 времени ответа              | ≤ 60 мс                 | > 60 мс 5 минут подряд — сигнал задолго до нарушения договора                                             |
| Доля опозданий                                             | < 0,1%                  | > 0,1% за 5 минут                                                                                         |
| Доступность                                                | 99.9%                   | доля 5xx > 0,1% за 5 минут                                                                                |

### 8.3. Трассировка и проверки

- **OpenTelemetry:** `request_id` из OpenRTB становится trace id; по трассе видно время каждого звена.
- **Tail-based sampling:** сохраняются все медленные (> 60 мс) и ошибочные запросы и 1% обычных — дёшево и полезно для
  разбора.
- **Синтетические проверки:** тестовые bid-request из точек, близких к партнёру, раз в 10 с — показывают время ответа
  так, как его видит DSP.
- **Дашборд по партнёру:** время ответа, RPS, no-bid, опоздания, начисленные штрафы — для разговора с партнёром на одном
  языке.

## 9. Отказоустойчивость самого слоя

- Envoy и Bid Gateway: минимум 3 пода в регионе, разнесённые по зонам доступности; PodDisruptionBudget не даёт
  обновлению выключить больше одного пода сразу.
- Конфигурация Envoy обновляется без перезапуска (xDS); изменения квот и весов применяются за секунды.
- Global LB проверяет `/healthz` каждого региона; при отказе региона трафик партнёров переводится в соседний.
