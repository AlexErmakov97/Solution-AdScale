# AdScale: архитектурное видение эволюции платформы

## Задача

AdScale — SaaS-платформа цифровой рекламы с аукционами в реальном времени (RTB). Интеграция с крупным DSP-партнёром
увеличит нагрузку с 15 000 до 18 000 RPS и ужесточит требования к времени отклика (стабильно ≤ 80 мс, штрафы за
деградацию и простой). Текущий монолит с одной инстанцией PostgreSQL уже работает на пределе: P95 110–120 мс при
требовании ≤ 100 мс.

Цели:

- **через 3 месяца** — подключить партнёра без деградации SLA: ≥ 18 000 RPS, P95 в пределах требования, масштабирование
  нагруженных компонентов, разделение критичных и некритичных потоков;
- **через год** — 50 000 RPS, микросервисы, событийная обработка, горизонтальное масштабирование, несколько регионов,
  доступность 99.9%.

## Краткие выводы

1. **Главная проблема** — синхронные обращения к единой PostgreSQL в критичном пути ставок, где они конкурируют с
   записью событий, финансами и тяжёлой аналитикой. По оценке, больше половины времени ответа — ожидание БД.
2. **Стратегия** — Strangler Fig: фасад перед монолитом и постепенный вынос сервисов с переключением трафика по частям и
   возможностью отката (ADR-001).
3. **Первый шаг** — Bidding Service без обращений к БД: данные в Redis, независимое масштабирование (ADR-002); события —
   через Kafka с пакетной записью (ADR-003); аналитика — на read replica; HA для PostgreSQL; мониторинг с первого
   месяца.
4. **Целевое состояние** — сервисы разделены по бизнес-контекстам и классам требований к времени отклика (hot path,
   near-real-time, back-office), у каждого своя БД, hot path разворачивается active-active в нескольких регионах.

## Открытые вопросы к бизнесу

1. Как DSP-партнёр считает 80 мс: включая сеть или только обработку, и по какому перцентилю.
2. Почему цель года — 50 000 RPS при ожидаемом двукратном росте (~30 000 RPS).
3. Допустимый перерасход бюджета рекламодателя при проверке по кешу.
4. Регионы размещения на этапе 2 и требования к хранению данных.
