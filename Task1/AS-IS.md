# AS-IS: анализ текущей архитектуры AdScale

## 1. Обзор

AdScale — гибридный монолит (C++ / Go / Python / Node.js), работающее на одном инстансе
PostgreSQL в одном production-кластере. Кеша, очередей, контейнеризации и автоматического деплоя нет. Документации по
архитектуре нет, мониторинга времени отклика по компонентам нет.

Текущие показатели: 15 000 RPS в пике, P95 времени отклика аукциона 110–120 мс при требовании не более 100 мс,
периодические деградации в часы пик, запас по производительности отсутствует.

### Компоненты и их роль

| Компонент            | Стек         | Назначение                                                       | Класс потока         | Работа с БД                         |
|:---------------------|:-------------|:-----------------------------------------------------------------|:---------------------|:------------------------------------|
| Ad Server            | C++, Go      | приём bid-request, идентификация пользователя, подбор кандидатов | критичный (hot path) | синхронное чтение данных таргетинга |
| Auction Engine       | C++          | бизнес-правила, взвешивание ставок, выбор победителя             | критичный (hot path) | синхронное чтение ставок и кампаний |
| Delivery Service     | Node.js      | HTML/JS-разметка баннера, формирование ответа                    | критичный (hot path) | — (вызывает Statistics)             |
| Statistics Service   | Python       | запись показов и кликов                                          | почти real-time      | прямая запись каждого события       |
| Financial Service    | Go           | списания, счета, балансы                                         | транзакционный       | транзакции и балансы                |
| Analytics Service    | Python       | аналитические SQL-запросы                                        | фоновый              | тяжёлые запросы к production-БД     |
| Advertiser Dashboard | Node.js + JS | UI рекламодателя: кампании, бюджеты, отчёты                      | интерактивный        | CRUD                                |

Внешние участники: DSP-партнёр (bid-request / bid-response по OpenRTB), платёжный шлюз (пополнение бюджетов),
рекламодатель, пользователь сайта или приложения.

### Критичный путь запроса (hot path)

```
DSP → Ad Server → [PostgreSQL] → Auction Engine → [PostgreSQL] → Delivery Service → (Statistics → [PostgreSQL]) → ответ DSP
```

На одном bid-request — минимум два синхронных обращения к БД. Если вызов Delivery → Statistics тоже синхронный (на
диаграмме это `Internal Call`), то на пути есть и третье — запись события.

## 2. Узкие места

| №  | Узкое место                      | Где                       | Почему это проблема                                                                                                               |
|:---|:---------------------------------|:--------------------------|:----------------------------------------------------------------------------------------------------------------------------------|
| B1 | Синхронные чтения БД в hot path  | Ad Server, Auction Engine | каждый запрос ждёт PostgreSQL; при росте нагрузки на БД время ожидания растёт нелинейно (очередь соединений, блокировки)          |
| B2 | Нет кеша                         | весь hot path             | данные кампаний, ставок и таргетинга меняются редко, но читаются на каждом из 15 000 запросов в секунду                           |
| B3 | Прямая запись событий без буфера | Statistics Service        | каждый показ и клик — отдельная транзакция; высокая нагрузка на запись, WAL, индексы и autovacuum конкурируют с чтениями аукциона |
| B4 | Аналитика на production-БД       | Analytics Service         | тяжёлые запросы занимают CPU, память и I/O, держат снимки данных и мешают vacuum; рост latency у всех остальных                   |
| B5 | Общий пул ресурсов монолита      | весь монолит              | отчёт в кабинете или пересчёт балансов отнимает CPU и соединения у аукциона; нагрузку нельзя изолировать                          |
| B6 | Пул соединений к одной БД        | все компоненты            | шесть компонентов из семи держат соединения к одной инстанции; в пик соединений не хватает, запросы ждут в очереди                |

## 3. Точки отказа

| №  | Точка отказа                                                      | Последствие                                                                                  |
|:---|:------------------------------------------------------------------|:---------------------------------------------------------------------------------------------|
| F1 | Одна инстанция PostgreSQL, нет реплик и HA                        | отказ или обслуживание БД останавливает всё: ставки, учёт событий, финансы, кабинет          |
| F2 | Один production-кластер                                           | авария в кластере или ЦОД — полный простой и штрафы DSP                                      |
| F3 | Монолит — один процесс деплоя и запуска                           | утечка памяти или падение в аналитике роняет аукцион; любой релиз требует перезапуска всего  |
| F4 | Ручной деплой без контейнеров                                     | высокий риск ошибки при выкатке, долгий откат                                                |
| F5 | Нет наблюдаемости по компонентам                                  | деградацию замечают по жалобам и штрафам; нельзя понять, какой компонент съел бюджет времени |
| F6 | Нет защиты от перегрузки (rate limiting, таймауты, load shedding) | при всплеске трафика система не отказывает лишнему трафику, а деградирует целиком            |

## 4. Проблемы, препятствующие масштабированию

1. **Масштабирование только целиком.** Нагружен в основном hot path, но добавить экземпляры Ad Server и Auction Engine
   отдельно нельзя — масштабируется весь монолит вместе с аналитикой и кабинетом.
2. **БД масштабируется только вертикально.** Новые экземпляры приложения лишь добавляют нагрузку на ту же инстанцию
   PostgreSQL. Горизонтальное масштабирование приложения упирается в БД.
3. **Смешаны разные профили нагрузки** в одной БД: OLTP (финансы, кабинет), высокочастотная запись (события), OLAP
   (аналитика), чтение с жёстким SLA (аукцион).
4. **Нет асинхронности.** Всё, что можно отложить (запись событий, пересчёт статистики), выполняется синхронно.
5. **Сильная связанность.** Компоненты общаются внутренними вызовами и через общие таблицы. Выделить компонент нельзя,
   не разобравшись, кто ещё читает и пишет его данные.
6. **Нет инфраструктуры для эволюции.** Без контейнеров, CI/CD и мониторинга нельзя безопасно выкатывать новые сервисы и
   переключать на них трафик.

## 5. Влияние архитектуры на время отклика

Мониторинга по компонентам нет, поэтому ниже — экспертная оценка распределения бюджета времени в пиковый час. Её первая
задача — подтвердить или опровергнуть замерами (см. Drivers.md, ограничение по наблюдаемости).

| Этап                                   | Оценка, мс (пик) | Что влияет                                                            |
|:---------------------------------------|:-----------------|:----------------------------------------------------------------------|
| Приём запроса, разбор OpenRTB          | 5–10             | сеть, TLS, парсинг JSON                                               |
| Ad Server: таргетинг + чтение БД       | 25–35            | синхронный запрос, ожидание соединения, конкуренция с записью событий |
| Auction Engine: чтение ставок + расчёт | 40–50            | синхронный запрос в hot path, блокировки от аналитики                 |
| Delivery: разметка                     | 10–15            | шаблонизация, сборка ответа                                           |
| Регистрация события (если синхронно)   | 5–15             | отдельная транзакция на каждое событие                                |
| **Итого**                              | **≈ 110–120**    | совпадает с наблюдаемым P95                                           |

Основной вывод: **больше половины бюджета времени — ожидание базы данных**, и именно эта часть растёт в пик. Ускорение
кода аукциона мало что даст, пока он синхронно ходит в общую БД.

При росте трафика до 18 000 RPS (+20%) нагрузка на запись событий растёт пропорционально, а время ожидания БД — быстрее,
чем линейно: при загрузке ресурса, близкой к 100%, очереди растут резко. Отсюда риск, описанный в кейсе: деградация до
150 мс и выше, тайм-ауты, проигранные аукционы и штрафы DSP.
